# OEP を使うプロジェクトのテストガイド

OEP プローブを使って、自分のクライアント、tool、組込みソフトウェアを検証するプロジェクト向けのガイドです。言語、target family、Arduino の利用有無を限定しません。テスト本体と合否基準は利用プロジェクトで管理し、通常は設置済みのプローブを使います。

責任と保証範囲の正本は [全体テスト方針](testing-policy.ja.md)。設備設定の新形式は [実機設定形式](hardware-schema.ja.md)と[配線の確定手順](hardware-configuration.ja.md)を参照してください。**offline loader/planner と仮想 smoke は使用可能ですが、実機 runner adapter と共有 session は未実装です。** 同梱の `.env` / TOML 雛形を置くだけで現行 runner が対応するわけではありません。現在の実行方法は利用プロジェクトの既存 runner に従い、以下の責任と判定を適用します。

## 1. 自分のプロジェクトで保証すること

| 利用方法 | 利用側が検査すること | プローブ提供側が検査すること |
|---|---|---|
| OEP client を実装する | framing、要求・応答、宣言の扱い、timeout、再送、session の回復 | protocol と宣言の適合、実 transport の動作 |
| 既存 client を利用する | 選択した経路、client の呼出し方、error の扱い、資源解放 | client 内部の通信処理と互換性判定 |
| flash/debug tool を作る | 対象識別、target 固有処理、readback、走行・debug、console 共存 | wire/DM の提供機能、資源と状態の分離 |
| target の driver/API を作る | target の振る舞い、外部信号、異常・復旧、独立 peer との通信 | fixture/capture の提供機能と計測条件 |
| 複数 target を連携させる | 両側の準備、役割、通信結果、片側失敗時の終了処理 | 接続・stream の上限と分離、共有 session |

利用側も設置済みプローブとの結合を検証します。提供側のテストが通ったことだけで、自分の組合せの成功を主張しません。一方、通常の利用テストに firmware 更新の合否判定を組み込む必要はありません。更新を評価する場合は、対象 image と変更を明示した別の検証として扱います。

## 2. 仮想環境から実機へ進める

1. ボード不要の単体検査で、入力、期待値、境界、error の扱いを確かめます。
2. 仮想プローブで、OEP の要求・応答、timeout、切断・再起動、資源競合、後始末を確認します。仮想 probe/target が保証できる範囲を明記します。
3. 設備を確認し、設置済みプローブと単体 target で、個体識別、書込み・readback、走行、control/log の経路を確認します。
4. target の API を、独立した刺激・観測で確認します。GPIO は外部入力・出力、UART は独立相手、時間精度は独立時計で検証します。
5. 必要な peer、負荷、異常・復旧、複数 target の契約を追加します。リリースに必要な対象と差分軸を所有側で決めます。

仮想プローブの版と依存は利用プロジェクトの lock/CI で固定し、入手方法を明示します。指定していない兄弟 checkout やホームから自動探索しません。必須の仮想検査で依存がない場合は準備エラーとし、テスト関数から return して成功にしません。

新コアの要求・session・再送・framingを検証する場合は、[適合検査入口](conformance-checks.ja.md)の `core-v1` を使えます。これはfn 0のみの最小profileです。flash/debugなどinterfaceを使う利用テストでは、該当interfaceが追従したtarget付きprofileを選び、そのSPEC版を記録します。

仮想での成功は電圧、配線、実時間精度、実 USB の品質保証にはなりません。また、自分の client と同じ実装系統の仮想プローブだけでは、共通の誤りを見逃す場合があります。規範からの期待値、独立実装、実機を組み合わせます。

## 3. 設備設定をテストから隔離する

テストコードは `dut` / `peer` / `observer` 等の役割と必要な機能・接続を宣言します。個体 ID、serial port、channel、target pad をコードへ固定しません。設備を交換したときは設定と確定記録を更新します。

新形式では、公開雛形をコピーして `.env` と `*.local.toml` を作り、Git 管理外にします。`.env` は `uv run --env-file .env ...` 等で明示的に渡し、個体と配線は TOML にまとめます。主要な指定は次の4つです。

| 設定名（新形式） | 用途 |
|---|---|
| `OEP_HW_INPUT` | 個体・電気条件・操作してよい探索範囲 |
| `OEP_HW_CONFIG` | 通常試験で使う確認済み構成 |
| `OEP_HW_RESULTS` | 今回の証拠の保存先 |
| `OEP_HW_LOCK` | 設備利用者が共通に使うロックの path |

設備情報は手で記入しても、任意の管理ツールから生成しても構いません。利用側が依存するのは設定形式であり、生成器や設備台帳ではありません。生成された `.env` で既存の秘密値や手編集を全体上書きしません。

現行 runner が独自 TOML や環境変数を使う場合は、その対応する設定を使います。移行時には adapter を明示し、新形式と旧設定を暗黙に混ぜません。

## 4. 配線を確認してから実行する

給電、GND、信号電圧、禁止 pin と探索範囲を先に確認します。debug の候補探索と、GPIO/UART の pad 対応の診断は別工程です。target の UID が取得できなければ手動識別の根拠を残し、chip family を個体識別として扱いません。

候補は全件保存し、複数候補の先頭を選びません。診断 image を書き込む処理は別途明示します。配線・probe・target・給電を変更したら影響する接続を再確認し、構成の世代を更新します。

通常の test collection や offline plan は port を開きません。実機実行では共通ロックを保持し、個体・宣言・必要接続の preflight から cleanup までを一つの占有区間にします。不一致があれば停止し、試験中に別 target を探して継続しません。

## 5. 複数 target と peer を使う

被試験の通信と、書込み・制御・log の経路を分けます。例えば USB host/device を試す場合、USB data が失敗しても両側の状態を独立 control から取得できる構成にします。RVSWD と DM console で必要な制御ができるなら、peer の UART 配線を一律に必須としません。

同じ probe を使う DUT/peer は一つの session と broker を共有し、target ごとの connection/stream を分けます。独立 fixture が別 session で取り合う構成にしません。必要な同時性を満たさない platform は、その契約に割り当てません。

両側の upload が終わった後、再問合せ可能な READY、build ID、役割を照合して通信を開始します。以前の起動 log を今回の成功と誤認しないよう、run ID や challenge を使います。片側の失敗でも両側の log と終了状態を保存します。

## 6. 使用版と証拠を残す

実行ごとにプロジェクトの commit/dirty、契約 ID、build profile、tool/client/仮想プローブ/実機プローブ/peer の使用版、実装する SPEC の版、protocol/interface revision、describe、image hash、個体、構成の世代・hash、役割、観測、判定、終了状態を記録します。取れない情報は unknown と理由を残します。firmware 文字列から source commit を推測しません。

通常の利用テストに数値的な最低 probe firmware 版を定義しません。使用した版を記録し、必要な機能と通信形式の互換性を client/tool が確認します。同じ版番号文字列であることだけを互換性の根拠にしません。候補 firmware の必須機能が欠落した場合は、その採用範囲の適合失敗として扱います。

DUT log、readback、capture、両側の READY、失敗時 snapshot を判定と紐付けます。元の失敗と cleanup の失敗を両方残します。テスト image や設定が残る場合は明記し、認証情報は保存しません。

## 7. skip と失敗を区別する

| 状況 | 扱い |
|---|---|
| 任意の実機 suite に設備設定を渡していない | 理由付き skip |
| 明示した設定・個体・接続が不在、不正、曖昧 | 準備・設定エラー |
| 任意契約の設備がない | 理由付き skip。未検証として残す |
| 採用機能の宣言・操作・READY が期待と異なる | FAIL。根拠なく設備不足へ分類しない |
| 必須のリリース契約が未実行・skip | リリース確認は未完了 |
| 契約自体が未整備、実装が未完成 | 未整備／未実装。PASS や対象外へ読み替えない |

リリース判断は自分のプロジェクトが所有します。必要な契約が成立しなければ、そのリリースの確認は未完了です。共有する結合試験の失敗を理由に、関係する全プロジェクトのリリースを一律に連動させません。

## 8. 不具合を切り分けて提供側へ渡す

個体・配線・電源・宣言の preflight、独立した既知 image、同じ契約を別 backend や別 probe で実行した結果を使って原因を切り分けます。すべての不具合で交換を必須にする必要はありません。再現できる最小の条件、期待値、使用版、log と終了状態を添えて、client・probe・target 実装の該当する所有側へ渡します。

probe 更新後の回帰を依頼された場合は、自分が所有するテスト入口と判定基準を提供します。更新する側は更新作業とその結果、影響する利用経路の確認を担当します。普段の利用テストが自動で probe を更新する流れにはしません。
