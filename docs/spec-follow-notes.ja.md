# 仕様追従で見つけた実装上の負担

oep-client-python を oep-spec `a09fa45` へ追従する作業（コア → 共通契約 → 標準インターフェースの順）で、
実装上かなり不便だと分かった仕様を記録する。仕様の見直しを検討するための材料であり、規範ではない。

各項目は、該当条項、実装で何が不便か、影響する側（host / probe / 仮想ベンチ）、考えられる代案を書く。
単に作業量が多いだけのものや、実装側の設計で解消できるものは載せない。

## 個別検討（2026-10-15）

対象は oep-spec `a09fa45` と、上の 1〜9 / E1。以下は仕様修正の要否についての提案であり、採用済みの規則ではない。
元の指摘・代案は残し、その前提の訂正もここに記す。仕様本文と Python の動作はこの追記では変更しない。

[版と安定性 §2.1](../../oep-spec/docs/versioning.ja.md)では、コアは暫定確定しており、既存の意味を変えるには
矛盾または独立実装が成立しない反例と境界検査が必要とされている。実装の負担が大きいことと、規則を変更しなければ成立しないことを分けて判断する。
下の「確認」は採用時に必要な試験の案であり、この検討で実行した結果ではない。

### 1. 重複 TLV の全コピー検証

**判断: 現時点では規則を維持する。** [core §2.3](../../oep-spec/docs/oep-core.ja.md)の規則は複雑だが、
既知 tag の構造・値・対応可否を副作用前に検証し、最初の値だけを実行へ渡す構成で実装できる。
op ごとに独立した検証が必要なこと自体は、仕様の矛盾ではない。値の検証を副作用のあるハンドラーから分け、同じ検証関数を全コピーへ適用するのが先である。

簡素化するなら、要求の既知・非反復 tag の重複を malformed にする案が、後続の値を部分的に無視する案より明快である。
ただし、今は有効な重複要求を新たに拒否する契約変更になる。critical の有無を除いた tag 番号で重複を判定し、
反復 tag は対象外とする必要がある。未知 tag は、将来の定義で反復可能か判断できないため、一律に重複拒否できない。
応答側の受信規則も、この変更から自動的に変えてはいけない（#8）。

後続の値域・unsupported を無視する案は、同じ tag の不正値を位置によって受理することになる。
採るなら意図した意味として明記し、critical の扱いも揃える必要がある。今回の負担の記録だけではコアの暫定基準を変更する根拠として足りない。

確認: 0x10 と 0x90 の重複、正常値の後の不正長・範囲外・未対応値、反復 tag、未知 non-critical / critical を分ける。
どの拒否でも外部への作用を起こさないことを確かめる。

### 2. 別プロセスからのセッション回復と corr

**判断: open / end を再送判定から外す案は採らない。** [core §5.1 / §6](../../oep-spec/docs/oep-core.ja.md)では、
古い要求を新しい要求と取り違えず、終了したセッションを復活させないことが目的である。
同じ ID の open を例外にすると、古い open が lease を更新したり、経路切替後の状態へ作用したりする余地を作る。
end だけの例外も、共通の再送契約から外れ、記録済みの結果と新規の終了処理を区別する追加規則が要る。
open の応答へ最後の corr を足すだけでは、その応答を得る open 自体が順序判定を通らない問題を解けない。

用途は二つに分ける。**資源を残して引き継ぐ**なら、session_id・corr の引き継ぎと旧送信者の停止が必要であり、
現在の [kept_session.py](../src/oep_client/kept_session.py) の番号予約・プロセス間ロックは妥当な方向である。
ただし、1024 ごとの予約だけで、任意回数のクラッシュや古い保存内容からの復帰まで安全と証明したわけではない。
最後に probe が受けた番号から半周未満であることと、旧経路の残りを再投入しないことも必要になる。

**資源を捨てて回復する**なら、lease 切れを待つほか、新しい ID で force open する既存の方法がある。
したがって上の「lease 切れまで待つしかない」は、他の所有者を奪う可能性のある force を使わず、保存状態もない場合に限る。
force は lock_state の表示だけで以前の自分を確定できないため、CLI が自動で選ぶ回復方法にはしない。
host ガイドに、この二つの用途と保存情報を失った場合の限界を追記することを推奨する。

corr を保存せず、他の所有者を奪わずに回復する要件が必要なら、期待する session_id を指定する任意の状態照会などを別途設計する。
その場合も、照会した corr はスナップショットにすぎず、旧送信者との競合や boot の変化を解決しない。順序の無条件リセットは避ける。

確認: 正常引き継ぎ、予約直後のクラッシュ、連続クラッシュ、保存情報の欠落、他の所有者への交代、lease 切れ、boot 変更、旧応答の残留。

### 3. port_speed の復帰保留

**判断: phase 3 へ入った後は取消なしとする簡素化を推奨する。** [link §3](../../oep-spec/interfaces/oep-if-link.ja.md)の
フレームを途中で壊さない保証は必要だが、idle だけを取り消せることはその保証に必須ではない。
期限後に要求が来たときの復旧を少し速くするために、保留理由・元の所有者・取消後の step 判定を組み合わせている。
host は既に速度喪失からの復旧を必要とするため、その利便性より状態遷移を減らす価値が大きいと考える。

案は、復帰条件が成立したら phase 3 を確定し、受信中の frame と必要な応答を現在の速度で完了して境界で phase 0 へ戻すこと。
新しい通知は始めず、後から来た要求で phase 2 に戻さない。core の見出し・再送・session 判定は今の順のまま維持し、
そこを通った新規 port_speed の全 step を cause 6 で拒否する。再送に過去の成功を返す規則とは分ける。
port_state の phase 3 は観測時点の状態なので、host はその応答を読んでいる間にも速度が戻りうると扱う。

代償は、idle の期限付近に着いた要求で保留を取り消せず、再探索が増えることである。
さらに、連続する新規要求を受け続けて復帰が延期されないよう、現在の frame / 応答を完了した境界と次の受信開始の優先順を明記する必要がある。
理由別の処理が完全に消えるわけではなく、end / force の応答後に戻る契約は残る。

確認: verify / idle / session 終了の各理由、TX / RX 途中と gap、期限直前・直後の commit、全 step、再送、別経路の force、連続受信。
既存の [復帰保留の監査判断](../../oep-bench/docs/spec-freeze-audit-followup.ja.md)を変更する提案なので、
表の一行だけでなく取消規則・host の復旧例・ベクタを一緒に更新する。

### 4. セッション間の console 出力

**判断: 用途上の不足はあるが、close の意味を変えるだけでは解けない。**
[console §2 / §3](../../oep-spec/interfaces/oep-if-console.ja.md)の収集は debug connection を使い、DATA0 / DATA1 へのアクセスも伴う。
セッション終了で connection とピンが解放される以上、バッファだけ残しても、その後の出力は受けられない。
「同じ番号で次の open に引き継ぐ」案は、[core §9](../../oep-spec/docs/oep-core.ja.md)の資源非再利用・セッション間非継承にも反する。

要件を、(a) 閉じる直前までに収集したログを後で読む、(b) host 不在中や probe 起動時から収集し続ける、に分ける。
(a) は host へ先に保存することで扱え、故障直前に保存できない分が残るという限界は既存の監査でも認識されている。
(b) は常駐 host / broker が現行仕様での解であり、常駐不要を製品要件にするなら独立した任意機能として設計する価値がある。

ただし、任意インターフェースにするだけで core §9 の例外にはできない。継続収集にはセッション外でピンと debug 接続を使う権限、
通常の attach との競合・明け渡し、boot 時の設定、容量上限、欠落の表示、停止・消去、異なる target へ接続し直したときの識別を定める必要がある。
保存済みログの読み出しと、動作中の console stream は別の対象にするのがよい。
まず (a)/(b) の必要性を定め、独立機能の設計ができるまでは現在の close と資源寿命を維持する。

確認: セッション終了前後、host 再接続、target reset、probe reboot、バッファ超過、ピンの競合、target 交換でログが混ざらないこと。

### 5. 購読解除時の未送信通知の破棄

**判断: 破棄する規則を維持する。元の代案の識別方法は成立しない。**
[core §10.2](../../oep-spec/docs/oep-core.ja.md)の共通見出しは fn と seq を持つが、購読の世代や session_id を持たない。
seq は購読ごとに 0 へ戻るため、新旧の通知が同じ fn・seq を持ちうる。個別 payload に世代がある場合も、購読の世代とは限らず、全通知には適用できない。
たとえば同じ fn の旧購読 seq 0 と新購読 seq 0 を置き換え応答の後に送ると、host は共通規則だけでは見分けられない。

送り始めた frame の完了と、未送信の破棄は、同じ経路の購読変更応答を新旧の境界にするために必要である。
未送信分の送信を許すなら、購読識別子を追加するか、旧通知を必ず応答前に排出する別の契約が要る。
前者は wire と host の負担を増やし、後者は詰まった経路で操作完了を遅らせ、応答優先との調整も必要になる。

実装では、未送信通知を fn 付きの frame 単位で保持し、送信開始時に byte 列へ渡す方法を推奨する。
byte リングが必要でも、frame の範囲と破棄対象を記録し、送信時に飛ばす構成を選べる。単一リングの途中から即時に詰め直すことまでは仕様は要求しない。
どこからを「送り始めた」とするかを実際の送信境界に合わせ、応答優先と送りかけ量の上限も満たす実装例を probe ガイドへ補うのが適切である。

確認: fn A の解除で fn B を残す、送りかけだけを完了する、購読変更の拒否で旧状態を保つ、経路変更・切断で旧通知を持ち越さない。

### 6. session_id 0 と corr の半周

**判断: セッションの順序を照会で進める仕様変更は不要。**
[host.py](../src/oep_client/host.py) は全要求で一つのカウンターを使い、`_session_room` で keepalive を補っている。
これはその番号割当方式の対処であり、[core §4.1](../../oep-spec/docs/oep-core.ja.md)が全 session_id の共通カウンターを要求しているわけではない。
別カウンターを無調整で使うのは誤りだが、session ごとの前進位置と、経路全体の使用中・旧応答待ちの番号集合を分けることはできる。

例として、セッション S の最後の corr が 100 なら、SID0 の照会が何周しても S の次候補は 101 のままでよい。
101 を SID0 が使用中、または古い応答が残りうる場合には、解決・排出を待つか、S の半周制限内で空いた番号を選ぶ。
再送後に余分な応答が残る場合の排出確認は現行 §4.1 の規則を使う。最古の未解決要求からの半周制限も別に守る。
空きが確認できなければ待機・経路回復が必要であり、無制限に新規要求を出せる方式ではない。

SID0 を所有セッションの順序へ数える案は、別の監視 host の照会で所有者の次要求を古いものにできる。
経路全体を基準にする案も、経路を切り替えても残る probe の再送状態との整合を新たに必要とする。
probe の順序状態を変えるより、host ガイドへ割当例を追加するのがよい。
現在の keepalive 方式も成立するが、番号管理のために lease を延長する点は実装方針として明示する。

確認: SID0 が 32768 件以上・一周以上進む場合、再送の余分な応答、未解決要求、0 のスキップ、二つのカウンターが同じ番号を候補にする場合。

### 7. 再実行してよい DMI 手順

**判断: 安全性を説明できる手順に限った例外を検討する。ただし、現状の代案の括りは広すぎる。**
[core §4.2 / §5.1](../../oep-spec/docs/oep-core.ja.md)、[common §3](../../oep-spec/interfaces/oep-if-common.ja.md)、
[debug §2](../../oep-spec/interfaces/oep-if-debug.ja.md)を合わせて検討する必要がある。
core の「失敗だけを根拠に」では追加の根拠の余地がある一方、§5.1 と common は結果不明の自動再実行を禁じている。
debug §2 は probe 自身の一部の値の復元には反復を認めるが、host の raw dmi 手順を同じ扱いにはしていない。
host へ例外を広げるなら、単なる文言整理として処理せず、適用範囲を定めた規則変更として検査する。

「同じ値を書く」「W1C」「読み取り用 command」という名前だけでは安全性の証明にならない。
たとえば W1C は、最初の clear 後に新しい事象で再び立った bit を、二度目の clear で消しうる。
DATA0 への同じ値の書き込みも autoexec の設定次第で別の操作を起こし、読み取り先に消費・clear などの副作用があれば読み取りの反復も安全とは限らない。
群全体を二度完了して同じ結果になることだけでなく、**任意の途中まで作用した状態から群をやり直せること**が必要である。

推奨する例外案は、target を知る host が、その操作に限って以下を確かめた場合だけ明示的に再実行するものとする。
対象 connection / boot / session が変わらず、先行処理が完了していること、hart・autoexec・console との競合を制御できること、
途中まで作用していても外部への効果を重ねずにやり直せること、最終的な結果と後始末を検証できること、回数・時間の上限があることを条件にする。
正常な completed failed を受けた場合と応答喪失は分け、応答喪失時は通常の再送・回復を先に行う。
その後も結果が不明なら、この条件を満たす根拠なしに新しい corr を送らない。

汎用 `held()` を無条件に元へ戻すことも、probe に「再試行可」の bit を渡すだけで raw 書き込みを反復させることも勧めない。
まず停止中の既知レジスタ読み取りなど、狭い手順に例外の根拠を付ける。現行の [riscv.py](../src/oep_client/riscv.py) に残る
応答 success 後の looks / agree 不一致による再実行も、同じ安全条件で評価する必要がある。

確認: 各手順の直前・直後での失敗、届いたが確認を失った書き込み、busy 中の再実行、autoexec、console の介入、途中の session / boot 変更。
安全な読み取りの回復だけでなく、resume・MMIO・W1C などの安全と証明していない群を拒む負例を用意する。
これらの根拠と境界検査が揃うまでは、現行の禁止規則に従う。

### 8. 応答 TLV の送信側と読み手

**判断: 「応答で bit 7 を立てない義務がない」という前提は訂正が必要。**
[core §2.2](../../oep-spec/docs/oep-core.ja.md)は既に「応答、出来事、データでは bit 7 は 0」と定めている。
同時に、受け取った場合には未知 tag として読み飛ばす規則もある。送信側の義務と、違反を受けた側の処理は両立する。

非反復 tag を送る側が重複させない規則は、正規の出力を一つに揃えるための追記候補とする。
ただし現行は重複時の読み方を定めているため、送信側の禁止を追加するなら新たな制約として扱う。
その追加だけで読み手の first-wins・長さ・bit 7 の処理を取り除けるわけではない。
「壊れた値は使わない」だけでは、壊れた最初のコピーの後に正常なコピーが来た場合の選び方も決まらなくなる。

反復した実装ミスへの対処は、文脈ごとの tag 定義を使う共通の読み手へ集めることを優先する。
既に [catalog.py](../src/oep_client/catalog.py) の `first_value` / `first_fixed` は最初のコピーと正確な長さを扱い、
応答では tag の bit 7 を落として既知 tag に読み替えない。可変長の値は count / length を含めて完全に検証する関数を用意し、
個別の読み手で `dict(tlvs)` や `len(v) >= n` を使う必要を減らす。
要求の critical 処理とは規則が違うため、同じ正規化処理を無条件に共用しない。

確認: 正常→重複、不正長→正常な重複、長すぎる値、bit 7 付き→通常 tag、反復 tag、未知 tag。
最初の壊れたコピーを後続の正常なコピーで救済しないことと、probe の出力が規則を守ることを別々に検査する。

### 9. DATA0 / DATA1 の復元責任

**判断: raw dmi に probe の暗黙の保存・復元を加える案は採らない。host の保存期間を短くするのを先に検討する。**
[debug §4](../../oep-spec/interfaces/oep-if-debug.ja.md)は、raw dmi に probe の追加アクセスを挟まないこと、
高水準 op はその op が触る前の値を戻すこと、次の op まで復元表を持ち越す義務がないことを明記している。
probe が resume の入口で DATA を読んでも、その値は host が既に書き換えた後であり、本来の郵便受けを復元できない。
以前から保存しておくには、raw 手順が一時的な利用なのか、意図した新しい値なのかを区別する契約が別に要る。

現在の [riscv.py](../src/oep_client/riscv.py) は `data_saved` を保持し、resume / reset / step / run などの前に `restore_data()` を呼ぶ。
この遅延復元は速さには有利だが、hart を走らせる全経路を覆う必要がある。
host の高水準レジスタ操作では、停止中に保存→操作→復元を完了する短い範囲に寄せることを推奨する。
一要求で収まらず複数の dmi に分かれる場合も、その間に走行や競合する console 操作を挟まない。
両 DATA を使う手順なら両方を対象にし、保存前の値が正しく読めたことと autoexec の状態を確かめる。

復元に失敗したら、後続の resume / reset / run を自動で続けず、状態が不明なことを呼び出し元へ返す。
`finally` を使うだけでは、通信断・プロセス終了時の復元を保証できない。ここまで保証する要件なら、
保存・操作・復元を probe 内の一要求で完結させる任意の高水準 op を検討する方が責任範囲を明確にできる。
一般の raw dmi まで透過的に変える必要はない。

「console 再同期で復元不要」の案も今の全方式には適用できない。SDI / DMDATA / dmseq は異なる方式であり、
DATA の一時値が正常な枠に見える場合まで必ず検出できるとは、この仕様からは言えない。再同期で未読の出力を復元できる保証もない。
host ガイドに復元範囲と失敗時の手順を補い、追加の probe op は具体的な性能・回復要件が出た時点で設計する。

確認: resume、reset mode 0、run、step、raw resumereq / ndmreset、操作途中の失敗、復元失敗、console が再開する直前。
DATA0 / DATA1 の一方だけを変える場合と両方を変える場合を含め、復元後に古い保存値を後の firmware 出力へ上書きしないことを確かめる。

4842f5f で、開き直した後の次の要求の前に、同じ条件で購読し直すようにした。U2 は `kept_session` の corr の予約で core に従っている。
U3〜U5 は仕様の判断を待つ。仮想ベンチと Python は a09fa45 の現行の規則のままにしてある。
U4 について、Python の `RiscvDm.held` は、応答 success の後に look / 二度読みが合わない群を、書き込みを含んでもやり直していた
（個別検討 #7 の指摘）。現行の禁止規則に合わせ、書き込みを含む群はやり直さず LinkNotHeld で止めるようにした。
そのため実機（CH32L103 と RVSWD）では失敗が増える。U4 で例外が決まったら、その条件を満たす群だけを再びやり直す。

### 追加の棚卸し（config から消えた項目）と、シリアルの口の素通しの実験

Arduino の `oep.probe.config` は、旧仕様のとおり plan（保存した割り当て）、slot（起動時からの debug 接続）、bind（シリアルの口がフレームの外で
1 つのストリームを運ぶ）、uart（fixture UART の保存した設定）、wifi（TCP で使う probe の接続先）の項目を持っていた。いまの仕様は label / idle /
disable だけで、transports §4 は「シリアル経路はフレーム専用、コンソールの生データを混ぜない」と bind を禁じている。

| # | 機能 | 実機での必要 | 判断 |
|---|---|---|---|
| R6 | wifi（接続先の保存） | TCP で使う classic ESP32 は、これが無いと OEP で接続先を設定できない（仕様は「別の定義で扱う」） | 拡張の候補。製品ごとの経路設定なので、まず firmware 自身の拡張で持ち、複数の製品で要るなら `oep.` にする |
| R7 | plan / uart の保存 | 治具の UART を起動時から受ける（bind の元） | 単独では戻さない（plan §0「保存した割り当ての再適用は host が明示的に行う」）。下の素通しの中でだけ扱う |
| R8 | bind（シリアルの口の素通し） | UART bridge しか口の無い probe（classic ESP32）では、これが無いと普通のシリアルモニタで target の出力を見られない | **戻す候補**（下の実験） |

実験（Python の仮想ベンチ、`VirtualSerialStream` に、セッションが無い間だけフレームの外へ生の byte を流させ、区切りの 0x00 を置いてから次のフレーム。
セッションの外の照会 confirm / describe / lock_state / clock を 60 回と、セッションの keepalive を 60 回、種ごとに 5 回）:

| 生の byte | 量（1 回の最大） | 成功 / 600 | 失敗 | 読み捨てた雑音 | 送り直し |
|---|---:|---:|---:|---:|---:|
| 無し | — | 600 | 0 | 0 | 0 |
| テキスト | 16 | 600 | 0 | 1276 | 146 |
| テキスト | 256 | 600 | 0 | 18303 | 130 |
| バイナリ（0x00 を含む） | 16 | 600 | 0 | 1269 | 153 |
| バイナリ（0x00 を含む） | 256 | 593 | 7 | 17919 | 187 |

テキストのコンソールでは失敗 0。送り直しは、host が CRC の合わない候補を壊れた応答とみなして、すぐ同じ要求を送るため（害は無い）。
0x00 を含むバイナリを大量に流すと 1% ほどが時間切れになる。セッションの中では生の byte を止めるので、セッションの要求には影響しない。

設計の方針（R8）: 素通しには、セッションの外で動くストリームの元が要る（fixture UART の plan も console のストリームもセッションの資源）。
core §9 の「セッションと独立して適用する設定の有無と作用は、その設定を扱うインターフェースが定める」の範囲で、`oep.probe.config` の任意の項目
`passthrough`（シリアルの口、fixture UART の fn、RX / TX の channel、baud、format）として定義する。どのセッションもその口・fn・ピンを使っていない間だけ
probe がその UART を動かし、受けた byte をフレームの外で口へ送り、口でフレームの外に来た byte を TX へ送る。セッションがその口から要求を送るか、
その fn やピンを取ったら、素通しはそのセッションが終わるまで止まる。v1 はテキストを想定した fixture UART だけを扱い、debug のコンソール（R1）は後で測る。

### R3' 連動トリガの試算（2026-10-15）

使っていたのは ESP32-P4 のミックスドシグナルで、ロジックが先導し、アナログがそれに従う。P4 のアナログの上限は 46 kHz（OepAnalog.h）で、一回取りだけ。
今の v1 で host が代わりにできること:

- capture-group の即時開始でロジックとアナログを同時に始め、ロジックだけは group の外で自分のトリガを持つ。トリガの trigger_ns と、アナログの開始時刻と速さから、
  host が後で切り出す。
- アナログを 1 秒張るのに要るのは 46 k × 2 B ≒ 92 KB。P4 の PSRAM なら 10 秒（約 0.9 MB）でも入る。合わせの誤差は 1 標本（約 22 µs）と開始時刻の不確かさの和。
- 取れなくなるのは「いつ起きるか分からない事象の前の区画」だけ。治具の試験は host 自身が DUT を動かすので、事象の時刻はおおむね分かる。

連動トリガを戻すと、capture §4 に follower のリング、トリガの遅れの上限、group の pretrigger の換算（P_k = ceil(P × rate_k / rate_t)）が戻る。
コアに近い共通部分が大きくなる割に、得るものは小さい。だから戻さない。需要が出たら firmware 自身の拡張として測る。

## 番号の管理と拡張の判断材料（2026-10-16）

### 今の規則

- core §12 の規則 7 は、他者が `oep.` のインターフェースに op、tag、値を足すことを禁じている。他者は自分の逆 DNS の名前のインターフェース（別の fn）にだけ足せる。
- このため、`oep.` の中の番号は project だけが振る閉じた空間になっている。

### 実例: 足したかったものは、どこに入るはずだったか

### 二つの考え方の比べ

**A. `oep.` を閉じる（今の規則 7）**

- 番号は registry だけで管理できる。かぶらない。
- そのかわり、ちょっとした追加でも仕様の変更（project の判断）か、インターフェースを丸ごと別に作ることが要る。
- #2 や #3 のように、別のインターフェースにすると資源（plan、group）をまたいでしまい、作れないものがある。
- この 2 日の作業でも、R1、R6、R8 の 3 回、仕様を変えた。

**B. 名前つきの拡張点だけ開ける**

- 番号を振るのは今までどおり project だけ（op、tag、enum の値）。
- 他者は、決まった拡張点に、逆 DNS の名前を付けて入れる。名前が識別子なので、他者どうしも、将来の仕様ともかぶらない。
- 実例 #9 の calibration の scheme と、設定の名前つきの項目（§1、§1.6）が、すでにこの形になっている。
- 費用は二つ。
  - 名前の分だけ byte が増える（20〜30 byte）。64 byte の frame の probe でも 1 つなら入る。重い用途は自分のインターフェースに置けばよい。
  - host は知らない名前を読み飛ばす。これは今の非 critical の TLV の規則と同じ。

### 分け方の案

**仕様で閉じる番号**（host が正しく動くために値を知っている必要があるもの）

- frame の role、resolution、outcome、reject reason、status、unavailable の cause。
- 状態、止まった理由、誤りの種類。
- 標準の op と、その標準の TLV。

これらは registry が振る。欠番を作らない。複数のインターフェースが使う値は、共有の空間として registry に明示する。今は次の空間が暗黙に揃えてあるだけになっている:

- wire の scan / attach の TLV、pin_role、attach_flags、scan_kind。
- capture の configure / answer の tag、trigger、state。

**拡張点**（他者が足す所。番号でなく名前で識別する）

1. 設定の項目: 名前（済み、§1）。
2. 標準の要求、応答、describe に他者の情報を足す所: 文脈ごとに 1 つの「名前つきの拡張 TLV」。値は名前と中身の組。知らない名前は、critical なら断り、そうでなければ読み飛ばす。#2 と #10 はこれで入る。
3. probe が選べるものを並べ、host が選ぶ所: describe の名前の並びにし、番号は並びの位置にする（fn と list と同じ形）。console の mechanism、netif、calibration の scheme（済み）が当たる。
4. 新しい機能: 自分の名前のインターフェース（今の規則のまま）。

### 決めたこと（oep-spec 2b3d89a）

B にした。core §12 の規則 7 を「他者は名前で識別する所からだけ足せる」に変えた。名前で識別する所は 3 つ:

- 名前つきの拡張 TLV（§2.2、どの文脈でも tag 0x7F）
- 名前の並び（§7.7、番号は 1 からの位置）
- 自分のインターフェース

### 連番か、範囲に意味を持たせるか（2026-10-16）

**今の仕様で、範囲に意味があるもの**（core §2.5）

| 範囲 | 何のためか | 判定 |
|---|---|---|
| インターフェースの op の 0x01〜0x0F（共通操作）と 0x10〜（固有） | 1 つの空間を 2 者（本体とインターフェース）が振る | 要る |
| reject reason、cause、status、describe の tag、mark の kind の 0x01〜0x3F と 0x40〜0x7F | 同じく 2 者（本体・共通部品と、インターフェース） | 要る |
| TLV の tag の bit 7（critical） | 受け手が、値を知らなくても扱いを決められる（断るか、読み飛ばすか） | 要る |
| 各空間の 0x80〜0xFF（未割当） | 持ち主が居ない | 意味は無い。将来の 3 者目に取っておくだけ。他者が名前を使えば要らない |
| fn 0 の op の 0x01〜0x0F（発見）と 0x10〜0x1F（セッション） | 持ち主は 1 者で、受け手は範囲を見ていない（ロックの要否は op ごとの表で決まる） | まとまりだけ。ただし core は実装の基準として暫定確定しているので動かさない |
| capture の configure の 0x40〜、answer の 0x50〜 | 持ち主は 1 者。見た目のまとまりだけ | 要らない |

**原則の案**

1. 範囲に意味を持たせるのは、次の二つのときだけにする。
   - (a) 1 つの空間を複数の持ち主が振るとき（本体・共通部品と、インターフェース）。
   - (b) 受け手が、知らない値の扱いを値の種類から決めなければならないとき（critical の bit）。
2. それ以外は、持ち主の範囲の先頭から、定義の順に連番にする。凍結前は欠番を作らない。凍結の後に廃止した番号は retired として残し、欠番になる。
3. 複数のインターフェースが同じ値を使うもの（wire の一族、capture の一族）は、一族の共有の空間として registry に 1 回だけ定義する。各インターフェースはその一部を使う。その一部が飛び飛びでも、空間そのものは連番になっている。
   - 例: 今は targetsel が scan では 0x06、attach では 0x02 と食い違っている。共有の空間にすれば 1 つの番号になる。
4. 他者は番号を取らない。名前つきの拡張点か、自分のインターフェースを使う。だから「他者用の番号の範囲」は作らない。
5. 外の仕様が決める値（SWD の ACK、eFuse、protocol のビット）は、外の値のままにする。ビットの集合はビットの位置で表す。

**影響の試算**

- インターフェースの番号は 329 個ある。インターフェースごとに詰め直すと 55 個が動く。
  - 大半は wire と capture の一族の「共有の空間の一部」で、3 の形にすれば動かす意味が変わる。
  - 凍結前に消した番号の跡は 6 か所ある:
    - reset_mode の 0x01
    - stopped_reason の 0x02（3 つのインターフェース）
    - configure の 0x41（logic、analog）
    - spi の describe の 0x42
    - capture-group の op の 0x13
    - analog の answer の 0x54 / 0x56
- core の番号（reject reason の 0x05 の欠番を含む）は、暫定確定なので動かさない。0x05 は retired として記録する。

**決めたこと（oep-spec 2b3d89a）**: 上の原則を core §2.5 に入れた。

- wire と capture の一族を registry の `family` で明示し、generator で検査するようにした。
- 欠番は詰めた。
- capture の error から、probe 固有の番号の範囲を外した。
- console の方式と config の netif は、名前の並びにした。
