# 仕様追従で見つけた実装上の負担

oep-client-python を oep-spec `a09fa45` へ追従する作業（コア → 共通契約 → 標準インターフェースの順）で、
実装上かなり不便だと分かった仕様を記録する。仕様の見直しを検討するための材料であり、規範ではない。

各項目は、該当条項、実装で何が不便か、影響する側（host / probe / 仮想ベンチ）、考えられる代案を書く。
単に作業量が多いだけのものや、実装側の設計で解消できるものは載せない。

| # | 条項 | 不便な点 | 影響 | 代案 |
|---|---|---|---|---|
| 1 | core §2.3「後続の同じtagも上の検証対象」 | 繰り返さない tag が 2 回来たとき、使わない 2 つ目以降の値まで、長さだけでなく値域・対応の有無（unsupported）も op ごとに検証しなければならない。共通の TLV 読み取りでは長さしか見られず、各 op のハンドラーに「全コピーを検証する」処理を足す必要がある | probe（各 op の実装）、仮想ベンチ | 後続のコピーは長さ（TLV の符号化）だけを検証し、値の検証は使う最初のコピーに限る。または重複そのものを malformed にする |
| 2 | core §4.1/§5.1（同じ session_id の新しい要求は、最後の corr から 1〜32767 先） | 別プロセス・別接続でセッションを引き継ぐ host（前回の実行が残したセッションを終わらせる CLI、別の接続での取り戻し）は、前の実行が最後に使った corr を知らないと要求が result_lost / malformed になる。終了処理のためだけに corr の状態を永続化する必要があり、本実装では 1024 番ずつ予約してファイルに書く仕組みを足した。分からなければ lease 切れまで待つしかない | host（CLI、再接続） | 新規要求として受け付けるのを「同一 session_id の open（新しい corr）」に限って順序判定から外す、または end だけは記録照合の対象外にする。もしくは probe が open の応答に最後の corr を返す |
| 3 | oep-if-link §3（port_speed の phase 3「復帰保留」） | 復帰条件が成り立っても送受信中のフレームを壊さないよう境界まで待ち、その間を phase 3 として扱う。保留の理由（試しの期限切れ・idle の期限切れ・セッション終了）ごとに、元の所有者の正常な要求で取り消せるか、step 0/1/2 をどう断るか、取り消し後にどの phase へ戻すかが違う。probe はフレームの送受信状態と保留理由と元の所有者を組み合わせて持つ必要があり、試験も場合分けが多い | probe（UART bridge）、仮想ベンチ | 保留中は理由によらず全 step を cause 6 で断り、取り消しを設けない（境界で必ず戻す）。host は port_state で戻ったことを確認してからやり直す |
| 4 | console §2（ストリームはセッション所有で、close・connection の解放・セッションの終わりでバッファごと解放）と probe.config（slot / bind の削除） | 1 回の実行ごとにセッションを開いて閉じる host（`oep` の各コマンド、試験のプロセス）では、コマンドとコマンドの間に target が出した出力（起動直後のメッセージ、リセット直後の 1 行目など）を拾えない。以前は閉じたストリームが同じ場所の次の open まで読め、at-boot の slot と bind でセッションの無い間も probe が受けていた。今は host が常駐してセッションを保ち続けるか、出力を取りこぼす前提で使うしかない | host（CLI、試験）、probe の使い勝手 | セッションの無い間も受け続ける「保持ストリーム」を任意機能として定める（宣言した probe だけが持つ。次のセッションの open で同じ番号と位置を返す）、または close を「閉じるが読める」にして同じ connection の次の open で続きを返す |
| 5 | core §10.3（購読の置き換え・解除で旧購読の未送信通知を捨て、送り始めたフレームは完了させる） | 通知を経路ごとの byte のリング 1 本にためる probe では、ほかの fn の通知を残したまま、その fn のまだ送り始めていないフレームだけを抜き取る必要がある。フレームの境目と fn をリングとは別に管理しなければならない | probe（通知の送信キュー）、仮想ベンチ | 置き換え・解除の後も旧購読の未送信分は送ってよいとし、host は seq（subscribe で 0 から）とフレームの世代で新旧を見分ける |
| 6 | core §4.1（session_id ごとに corr を 1〜32767 進める。session_id 0 の照会でセッションの番号を半周以上飛ばさない） | 1 本のカウンターで全 session_id の corr を振る host では、セッション中に session_id 0 の照会（lock_state、clock など）を 32768 回以上続けると、次のセッションの要求が result_lost になる。番号の再使用禁止（§4.1）があるので session_id 0 用に別カウンターを持つのも難しく、本実装は半周に近づいたらセッションの keepalive を 1 つ挟む（lease も延びる）ことで避けた | host | probe の順序判定を「最後の corr から半周」ではなく session_id 0 を含む経路全体の corr の前進で見る、または session_id 0 の要求も同じセッションの順序に数えてよいと定める |
| 7 | common §3「failedやdone 0は…書き込みが届かなかった保証ではない…新しいcorrによる自動再実行…で同じ書き込みを繰り返さない」、core §4.2「hostは失敗だけを根拠に状態変更を自動再実行しない」 | 落ちやすい debug link（RVSWD の先の CH32L103 は hart の状態を変えた後 0.7〜2 ms ほど link が落ちる）で、`RiscvDm.held` は DMI の一群（cmderr の消去、DATA0 の sentinel、abstract command）を、probe が status line / timeout / wait で失敗を返したときに丸ごとやり直して乗り切っていた。群は 2 度走ってよいもの（同じ値の書き込み、何も変えない読み取り）に限って作ってあるが、規則は冪等かどうかを区別しない。従って書き込みに達した失敗はやり直せず、その場で StepListError になる（read_register などが落ちた link で失敗しやすくなる） | host（riscv-dm のクライアント） | 結果が同じになる書き込み（同じ値の再書き込み、W1C、読み取り専用の abstract command）だけの群は、失敗の後に新しい corr で再実行してよいと定める。または dmi に「この一群は再実行してよい」の印を設け、probe 側で線の再試行を許す |
| 8 | core §2.2 / §2.3（応答・出来事・データの読み手: 繰り返さない tag は最初のコピーを使い、定義どおりの長さでなければ壊れたものとして使わず、bit 7 の立った TLV は知らない tag として読み飛ばす） | 送る側（probe）に「繰り返さない tag を 2 度送らない」「応答で bit 7 を立てない」義務が無いため、host は応答の TLV を読むすべての箇所（describe の各 tag、cause / fn、owner、unit_id、capture の actual_*、dpc、target_id など）でこの 3 つを守らなければならない。素直な `dict(tlvs)` は最後のコピーを使い、`len(v) >= n` は長すぎる値を通すので、追従の第 4〜7 回のレビューで同じ種類の誤りが合わせて 20 か所以上見つかった。読み手の数だけ同じ防御を書くことになる | host、検査器 | probe は繰り返さない tag を応答・出来事・データで 2 度送らず、bit 7 も立てないと定める（違反は probe の欠陥とし、検査器が確かめる）。読み手の規則は「壊れた値は使わない」の 1 つに減らせる |
| 9 | debug §4「host は、dmi の要求で抽象コマンドなどを使って DATA0 / DATA1 を変えたら、hart を走らせる前に、変える前の値を書き戻す」 | hart が走り出す経路は resume だけでなく、reset（mode 0）、run、raw dmi での resumereq / ndmreset、コンソールの再開など何本もあり、host はそのすべての前で「DATA0 / DATA1 を変えたか」を覚えて書き戻す必要がある。追従のレビューでは reset の前（第 5 回）と raw の resumereq の前（第 6 回）で戻し忘れが見つかった。戻し忘れると、走り出した firmware のコンソールの郵便受けを古い値で上書きする | host（riscv-dm のクライアント、生の dmi を使う道具） | hart を走らせる高水準の op（resume、reset、run）は probe が覚えている郵便受けの値を戻してから走らせる。または、コンソールの方式が DATA0 / DATA1 の食い違いを検出して同期し直す手順を持ち、host の書き戻しは不要にする |

## 仕様側の誤りと思われるもの

不便さではなく、仕様の本文と検査ベクトルが食い違っているもの。クライアントの試験はその食い違いを明示的に確かめており、
仕様側が直れば試験が知らせる。

| # | 箇所 | 食い違い | クライアントの扱い |
|---|---|---|---|
| E1 | `tests/vectors/interface_profiles.json` の「mode0 SPI target」（`tools/oepvectors1.py` の `interface_profiles`） | describe の max_length（tag 0x03）を `struct.pack('<I', 50)` の 4 byte で書いている。core §7.4 は max_length を u16 と定める | core §2.3 のとおり壊れた TLV として使わない。`test_interface_profiles_as_the_host_reads_them` がその 1 件の max_length を壊れたものとして確かめ、ベクタが直れば失敗して知らせる |
